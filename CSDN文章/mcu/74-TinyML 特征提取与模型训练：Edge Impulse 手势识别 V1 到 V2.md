# TinyML 特征提取与模型训练：Edge Impulse 手势识别 V1 到 V2

上一篇完成了 **STM32 → MPU6050 → Python → CSV** 的数据采集链路，本篇正式进入这个项目最核心的 TinyML 环节：

> **原始传感器数据 → 特征提取 → 特征空间 → 分类模型 → 模型迭代**

这一步的意义并不是“调用一个 AI 模型看看能不能识别”，而是要真正理解：**为什么这些加速度数据能够被模型区分，以及模型效果不好时应该从哪里改。**

本项目最终使用 Edge Impulse 完成数据集处理、Spectral Features 特征提取和分类模型训练，并形成 V1、V2 两次迭代。项目仓库中已经保留了对应的特征空间和训练结果截图，本文直接结合这些实际资料分析。

---

## 一、先明确：STM32 采集到的到底是什么？

本项目使用 MPU6050 采集三轴加速度：

- `accX`
- `accY`
- `accZ`

STM32 端按照 **50Hz** 的采样节拍工作，每次记录 100 个三轴数据点。

因此一次完整动作窗口包含：

```text
100 samples × 3 axes = 300 dimensions
```

也就是说，模型最终面对的并不是一句“这是左右挥动”，而是一段长度固定的数字序列。

例如：

```text
t0   ax0   ay0   az0
t1   ax1   ay1   az1
t2   ax2   ay2   az2
...
t99  ax99  ay99  az99
```

如果直接把这些原始数据交给分类器，模型当然可以尝试学习，但对于 MCU 端部署而言，**如何把时域信号压缩成更有区分度的特征**就非常重要。

---

## 二、为什么不能只看某一个轴？

这是这个项目实际开发过程中非常容易踩到的坑。

例如：

- 左右挥动可能主要体现在 X/Y 方向；
- 前后快速晃动可能主要体现在另一个轴；
- 上下抬起通常会明显影响 Z 轴；
- 静止状态下，Z 轴还会包含约 1g 的重力分量。

因此，一个动作并不是简单的：

```text
X 变大 → 某动作
```

而更接近：

```text
三轴时序变化
    ↓
幅值变化 + 频率变化
    ↓
特征
    ↓
分类
```

项目 README 中也记录了后续端侧显示调试时遇到的“单轴盲区”：原示波器只观察 X 轴时，上下移动和前后移动无法得到直观波形。最终工程中改成了三轴动态幅值比较和主导轴追踪。这个问题也说明，**多轴传感器的数据不能简单粗暴地只取一路。**

---

## 三、为什么选择 Spectral Features？

对于手势识别而言，传感器数据不仅有“幅度”，还有非常明显的“变化速度”和“周期性”。

例如：

| 手势 | 典型信号特点 |
|---|---|
| `idle` | 三轴整体变化较小，主要保留重力分量 |
| `wave_lr` | 水平运动产生明显动态变化 |
| `shake_fast` | 高频、快速变化明显 |
| `lift_ud` | 垂直方向变化更加突出 |

因此，本项目没有单纯依赖原始时域数据，而是在 Edge Impulse 中配置了 **Spectral Features**。

可以把它简单理解为：

```text
时域信号
   ↓
分析一段时间窗口里的频率成分
   ↓
得到频域特征
   ↓
让不同动作在特征空间中更容易分开
```

这就是 TinyML 中非常重要的一条思路：

> **不是把所有原始数据原封不动塞进神经网络，而是先找到对任务有意义的表示。**

## 五、什么叫“特征空间分离”？

假设最终提取出了两个特征：

```text
Feature 1
Feature 2
```

那么每一个采样窗口都可以看成二维空间中的一个点：

```text
        Feature 2
            ↑
            │       ● ● ●
            │      ● ● ●
            │
            │                  ▲ ▲ ▲
            │                 ▲ ▲ ▲
            └────────────────────────→ Feature 1
```

如果：

- `idle` 聚在一块；
- `wave_lr` 聚在另一块；
- `shake_fast` 聚在第三块；
- `lift_ud` 聚在第四块；

那么分类器就比较容易学习。

反过来，如果不同类别大量重叠：

```text
● ▲ ● ▲ ●
 ▲ ● ▲ ●
```

模型就很容易出现混淆。

所以在 TinyML 项目中，**看 Feature Explorer 并不是“看个漂亮的散点图”**，而是在检查数据经过特征提取后是否已经具备分类价值。

## 六、V1 暴露的问题

V1 最大的价值不是“效果不错”，而是它帮助我们发现了后续优化空间。

项目实际记录中，V1 存在两个值得关注的问题：

### 1. 特征生成耗时偏高

V1 的特征生成耗时估算约为：

```text
≈ 11 ms
```

对于 PC 端来说，这几乎可以忽略；但对于 STM32F103 这样的 MCU 来说，DSP 处理时间会直接影响整个端侧推理预算。

因此 TinyML 的目标并不是：

> 只要准确率高就行。

而是：

> **准确率、RAM、Flash、DSP 时间和神经网络推理时间需要一起考虑。**

### 2. 特征空间仍存在孤立误判点

V1 的训练结果中存在孤立误判点，说明当前特征提取参数还没有把所有类别完全拉开。

因此下一步不是盲目“多训练几次”，而是回到前面的特征工程阶段。

## 七、V2：调整特征提取参数

第二版的核心思路非常明确：

> **优化前级特征提取，而不是单纯堆大模型。**

项目中保存了 V2 的结果：

```text
03_Images_and_Results/
├── ei_feature_explorer_V2.png
└── ei_model_training_metrics_V2.png
```

V2 调整频域分析窗口与相关特征提取参数后，得到两个非常直接的结果：

### 特征处理时间

```text
V1 ≈ 11 ms
V2 ≈ 2 ms
```

也就是说，端侧特征处理耗时大幅下降。

### 特征空间

V2 中 4 类动作在特征空间中的聚类间距更加清晰。

项目记录的训练混淆矩阵验证结果达到：

```text
100% accuracy
```

这里需要特别强调：

> **100% 是当前数据集/验证划分上的结果，并不等价于真实世界中的 100% 泛化准确率。**

当前数据集规模仍然比较小，因此这个结果主要说明：**当前采集数据在特征空间中已经具有较好的可分性。**

## 八、V1 → V2 到底优化了什么？

把两次迭代放在一起看，会更清楚：

| 项目 | V1 | V2 |
|---|---:|---:|
| 特征处理 | 初始配置 | 优化后的配置 |
| 特征处理耗时 | ≈11ms | ≈2ms |
| 特征空间 | 存在孤立误判点 | 聚类间距更清晰 |
| 训练验证 | 存在改进空间 | 混淆矩阵达到 100% |
| MCU 部署意义 | 可验证 | 更适合端侧实时推理 |

这次迭代让我真正体会到 TinyML 和普通“训练一个模型”的区别：

**模型本身只是整个系统的一部分。**

真正部署到 MCU 后，需要同时关心：

```text
传感器采样
   ↓
窗口切片
   ↓
DSP / 特征提取
   ↓
神经网络推理
   ↓
结果输出
```

任何一个环节太慢，都可能影响最终系统体验。

---

## 九、为什么“小数据集”也能跑出很高准确率？

当前项目使用 4 个类别，每类 15 个样本：

```text
4 classes × 15 samples = 60 samples
```

这个规模对于一个真正要投入使用的手势识别系统来说显然还不够大。

但是对于当前项目阶段，它有一个非常重要的作用：

> **验证“采集 → 特征 → 训练 → 部署 → 推理”的完整工程链路。**

因此现阶段不应该把目标定义为：

> “用 60 个样本训练出一个商业级模型。”

而应该定义为：

> “用足够小的数据集快速验证 TinyML 端侧部署链路，并通过 V1/V2 迭代找到影响模型效果和性能的关键因素。”

后续第二阶段再扩充数据集，测试不同速度、幅度、握持方式以及不同使用者之间的变化，才能真正评价模型的泛化能力。

## 十、一个非常重要的 TinyML 思维转变

这次项目让我对“机器学习”有了一个更工程化的理解。

以前容易把流程理解成：

```text
数据 → 模型 → 准确率
```

但真正部署到 STM32 后，流程实际上是：

```text
┌───────────────┐
│  传感器采集    │
└───────┬───────┘
        ↓
┌───────────────┐
│  数据集构建    │
└───────┬───────┘
        ↓
┌───────────────┐
│  特征工程      │
└───────┬───────┘
        ↓
┌───────────────┐
│  模型训练      │
└───────┬───────┘
        ↓
┌───────────────┐
│  模型压缩/导出 │
└───────┬───────┘
        ↓
┌───────────────┐
│  STM32 部署    │
└───────┬───────┘
        ↓
┌───────────────┐
│  端侧推理      │
└───────────────┘
```

所以 TinyML 真正有价值的地方，是把 **算法问题和嵌入式工程问题连接起来**。
