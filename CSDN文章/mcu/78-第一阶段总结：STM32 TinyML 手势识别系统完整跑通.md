## 二、最终系统做到了什么？

当前系统基于 STM32F103ZET6，使用 MPU6050 采集三轴加速度，在 MCU 本地完成 TinyML 推理，并通过 OLED 显示结果。

系统支持 4 类手势：

| 类别 | 含义 |
|---|---|
| `idle` | 静止 / 待机 |
| `wave_lr` | 左右挥动 |
| `shake_fast` | 快速晃动 |
| `lift_ud` | 上下抬起 |

当前完整链路为：

```text
MPU6050
   ↓ I2C1
STM32F103ZET6
   ↓
100 × 3 轴加速度采样
   ↓
300 维浮点数据
   ↓
Edge Impulse DSP
   ↓
TinyML 分类模型
   ↓
4 类概率输出
   ↓
Argmax
   ↓
手势 + Confidence
   ↓
OLED / USART1
```

项目 README 中记录的最终阶段状态是：端侧推理已经完成实机验证，平均推理时间从早期约 72ms 优化到约 32ms。fileciteturn55file0L2-L2

## 三、硬件组成

当前第一阶段没有追求复杂硬件，而是围绕“能够完整验证 TinyML 端侧闭环”进行配置。

| 模块 | 作用 |
|---|---|
| STM32F103ZET6 | 主控与端侧推理 |
| MPU6050 | 三轴加速度采集 |
| 0.96 寸 SSD1306 OLED | 状态、波形与识别结果显示 |
| KEY0 | 启动一次手势采样 |
| USART1 | 调试信息、概率与推理耗时输出 |

接口分工：

```text
I2C1 → MPU6050
I2C2 → OLED
USART1 → PC / VOFA+
KEY0 → 采样触发
```

将传感器和 OLED 放在不同 I2C 总线上，也是这次工程实践中一个比较重要的细节：显示刷新不应该成为传感器采样链路的主要阻塞因素。

## 五、模型经历了 V1 → V2 两次迭代

第一版模型跑通以后，并没有直接把它当成最终结果。

### V1

V1 主要用于验证完整训练与部署流程。

当时已经能够完成特征提取和分类，但存在两个明显问题：

- 特征生成耗时相对较高；
- 特征空间存在孤立误判点。

### V2

随后调整特征提取窗口和参数。

结果是：

```text
特征处理估算时间
约 11ms
 ↓
约 2ms
```

同时 4 类动作在特征空间中的聚类更加清晰。

当前验证集混淆矩阵达到 100% 的验证准确率，但这里必须强调：

> 100% 只代表当前数据集和验证划分上的结果，不代表模型已经具备现实环境中的 100% 泛化能力。

这也是 TinyML 项目必须保持的工程判断。

## 六、真正困难的部分，其实发生在“部署以后”

如果只看训练平台，整个项目似乎很简单：

```text
上传数据 → 训练 → 导出模型
```

但是把模型真正放进 STM32 后，问题才开始集中出现。

第一阶段主要解决了以下问题。

### 1. Semihosting 调试死锁

标准库配置导致程序在嵌入式环境中进入半主机相关路径，最终表现为程序异常卡死。

解决思路：

```text
关闭 / 剥离 Semihosting
↓
改为正常串口调试
```

### 2. DSP `-1002` 内存问题

Edge Impulse 的 DSP 阶段需要额外临时内存，而 STM32 工程默认堆空间不足。

最终调整启动文件中的内存规划，为 DSP 和模型运行提供足够空间。

### 3. TFLite Micro 依赖爆炸

直接把完整 TFLite Micro 解释器加入工程，会拉入大量额外依赖。

而 EON Compiler 已经将模型关键计算路径静态展开。

因此最终采用：

```text
EON 静态模型
+
Safe Stub
+
静态内存
```

减少不必要的动态解释器依赖，并解决了 HardFault。

### 4. 传感器量纲失配

这是一个非常典型、也非常值得记录的问题。

MPU6050 底层输出的数据单位和训练数据所采用的单位没有完全对齐时，即使：

```text
代码没报错
模型能运行
```

模型也可能完全“不认识”输入。

本项目最终统一了训练与推理阶段的数据单位，使输入分布重新匹配。

### 5. CMSIS-DSP RFFT 限制

当前窗口配置出现过 16 点 RFFT 无法命中 CMSIS-DSP 硬件优化路径的问题。

最终通过 SDK 的软件 FFT fallback 保证了功能闭环，同时进一步理解了：

> “算法能运行”和“算法走到了硬件优化路径”是两件不同的事情。

### 6. OLED 显示空间不足

最开始的显示逻辑没有充分考虑 128×64 OLED 的像素预算。

后来通过主导轴追踪、紧凑 6×8 字库等方式，把调试信息压缩到有限屏幕空间中。

## 九、第一阶段最大的经验：能跑 ≠ 做完

这一点是我在这个项目中最重要的认识之一。

比如：

```text
模型能训练
    ≠
模型能部署
```

```text
模型能部署
    ≠
模型输入正确
```

```text
模型能推理
    ≠
推理足够快
```

```text
验证集 100%
    ≠
现实环境 100%
```

```text
程序能运行
    ≠
工程已经可靠
```

真正的工程迭代实际上是一个不断平衡的过程：

```text
Accuracy
   ↕
Latency
   ↕
RAM / Flash
   ↕
稳定性
   ↕
可维护性
```

这也是从“做实验”走向“做项目”最明显的区别。
