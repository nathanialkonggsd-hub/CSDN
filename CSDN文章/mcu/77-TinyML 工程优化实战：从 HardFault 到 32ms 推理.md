# TinyML 工程优化实战：从 HardFault 到 32ms 推理

> 系列：基于 STM32 与 TinyML 的端侧手势识别系统
>
> 本文是第 77 篇，重点复盘模型真正跑上 STM32F103 之后遇到的工程问题：HardFault、DSP 内存不足、传感器量纲失配、FFT 硬件约束、示波器单轴盲区以及 OLED 显示遮挡。

## 一、为什么模型能跑还不等于项目完成？

前面的文章已经完成了：

```text
MPU6050
   ↓
STM32 采集
   ↓
Python / CSV
   ↓
Edge Impulse
   ↓
特征提取 + 模型训练
   ↓
C++ 模型导出
   ↓
Keil / STM32F103
   ↓
端侧推理
```

但在实际嵌入式环境里，“编译成功”只是起点。

PC 上几乎不需要考虑的事情，在 STM32F103 这样的 Cortex-M3 平台上都会变成现实问题：

- RAM 到底够不够？
- C/C++ 运行时会不会引入额外依赖？
- DSP 算法是否满足 MCU 的硬件约束？
- 训练数据的单位和传感器输出是否一致？
- OLED 的显示是否会影响真正的采样与推理？
- 识别速度是否足够实时？

这一篇就是把这些问题逐个拆开。

## 二、HardFault：模型初始化为什么会直接死机？

### 1. 最初的问题

Edge Impulse 模型启用了 EON Compiler 静态展开：

```cpp
EI_CLASSIFIER_COMPILED = 1
```

理论上，神经网络已经被转换为静态 C++ 代码，不应该再依赖完整的 TensorFlow Lite Micro 动态解释器。

但实际链接过程中，仍可能出现算子注册、临时 Tensor、解释器相关符号。

如果把官方完整的 `micro_interpreter.cc`、`micro_allocator.cc` 等文件全部加入工程，依赖会迅速膨胀，并继续牵出 FlatBuffers、内存规划器等组件。

这对于 STM32F103 来说并不是一个好的方向。

### 2. 更危险的错误方案

一开始很容易想到：

```cpp
return nullptr;
```

看起来既然 EON 已经静态完成模型计算，那些动态接口不用就好了。

但问题在于：**调用方未必只检查返回值。**

如果后续代码仍然向这个返回地址写入 Tensor 元数据，那么：

```text
nullptr
  ↓
写入结构体
  ↓
非法地址访问
  ↓
Cortex-M3 HardFault
```

这也是嵌入式开发中非常典型的一类问题：

> “函数逻辑上不需要这个对象” ≠ “调用链上可以返回空指针”。

### 3. 最终方案：Safe Stub

项目最终没有继续引入完整动态解释器，而是在 `model_runner.cpp` 中使用安全存根，为需要的接口提供合法的静态实体。

核心思想可以概括成：

```text
EON 静态模型
      ↓
真正需要的计算已经静态展开
      ↓
裁剪 TFLite Micro 动态依赖
      ↓
保留最小接口
      ↓
用静态 Tensor / Buffer 提供合法地址
      ↓
避免 nullptr 解引用
```

这不是简单的“把错误隐藏掉”，而是根据实际运行路径裁剪依赖。

**工程启示：在资源受限 MCU 上，依赖裁剪本身就是优化。**

## 三、DSP `-1002`：不是模型错，而是内存不够

### 1. 现象

第一次运行 `run_classifier()` 时，串口出现 DSP 错误：

```text
-1002
EI_IMPULSE_DSP_ERROR
```

这时候模型已经能够进入推理流程，因此很容易误以为是模型本身有问题。

实际上，排查方向应该首先包括：

```text
模型输入
↓
DSP 特征处理
↓
临时矩阵 / FFT 缓冲
↓
内存分配
```

### 2. STM32 的默认堆空间太小

项目使用的 STM32F103ZET6 只有 64KB SRAM。

而 MDK 工程的启动文件最初给出的堆空间并不适合当前 DSP 工作负载。

最终项目调整了：

```asm
Stack_Size      EQU     0x0000800
Heap_Size       EQU     0x00002800
```

也就是：

| 区域 | 大小 |
|---|---:|
| Stack | 2KB |
| Heap | 10KB |
|

实际启动文件中就是这一配置。fileciteturn54file0

### 3. 为什么不能无限加？

因为 STM32F103ZET6 总 SRAM 只有 64KB。

所以调整 Heap/Stack 时必须同时考虑：

```text
全局变量
+ 静态模型数据
+ raw_features
+ OLED 缓冲
+ Heap
+ Stack
+ 其他运行时数据
≤ SRAM
```

因此真正的工程思维不是：

> “报 OOM，就把 Heap 加大。”

而是：

> “找出内存生命周期，并让所有区域在芯片 SRAM 预算内工作。”

## 四、最隐蔽的 Bug：传感器单位和模型单位不一致

这是整个项目里非常值得记录的一次排障。

### 1. 症状

内存问题解决以后：

- 模型可以正常执行
- `idle` 比较容易识别
- 其他动作置信度异常
- 概率分布趋于扁平
- 某些动作 confidence 只有约 `0.23`

如果只看代码，模型已经“正常运行”，很容易把问题归结为模型训练效果。

实际上问题出在数据。

### 2. g 和 m/s² 的差别

MPU6050 数据经过底层换算后，项目中的传感器数据以重力加速度倍数 `g` 表示。

而训练数据使用的是国际单位制加速度 `m/s²`。

二者关系：

```text
1 g ≈ 9.80665 m/s²
```

因此，如果训练阶段输入：

```text
1.0
```

代表的是 `1 m/s²`，而推理阶段输入：

```text
1.0
```

却代表 `1 g`，模型看到的实际上已经不是同一个数据分布。

### 3. 修复

在填充模型输入时统一量纲：

```c
value_ms2 = value_g * 9.80665f;
```

这个 Bug 给项目带来的最大启示是：

> TinyML 的输入数据契约不仅包括“维度”和“顺序”，还包括单位。

以后做传感器模型时，建议明确记录：

| 项目 | 必须固定 |
|---|---|
| 采样率 | 50Hz |
| 轴顺序 | X/Y/Z |
| 窗口长度 | 100 samples |
| 输入维度 | 300 |
| 单位 | m/s² |
| 数据排列 | 与训练阶段一致 |

## 五、CMSIS-DSP：为什么硬件 RFFT 没有命中？

项目运行过程中出现过类似日志：

```text
INFO: HW RFFT failed, FFT size not supported.
Must be a power of 2 between 32 and 4096,
(size was 16)
```

### 1. 原因

ARM CMSIS-DSP 的硬件优化 RFFT 对输入长度存在约束。

当前项目的某个频域切片窗口为：

```text
16 points
```

而 `arm_rfft_fast_f32` 所要求的长度范围从 32 到 4096，并且必须是 2 的整数次幂。

因此：

```text
16
↓
不满足硬件 RFFT 条件
↓
硬件优化路径无法使用
```

### 2. 但为什么程序还能继续？

Edge Impulse 的处理链并没有因此整体失败，而是可以退回软件 FFT 路径完成频谱计算。

项目中实际表现为：

```text
CMSIS-DSP HW RFFT
        ↓
      不支持
        ↓
   软件 FFT fallback
        ↓
   继续生成特征
        ↓
      模型推理
```

因此这不是一个“模型无法运行”的致命错误，而是一个**性能路径没有命中**的问题。

### 3. 工程取舍

如果强行为了命中硬件 RFFT 而修改模型输入窗口，就会影响：

- 特征分布
- 模型训练配置
- 模型大小
- 推理耗时

所以当前阶段选择保持模型逻辑正确，让 SDK 自动软件降级，是更稳妥的方案。

后续如果继续优化，可以专门研究：

> 如何重新设计采样窗口，使 TinyML 特征提取同时满足模型效果和 CMSIS-DSP 硬件约束。

## 六、示波器为什么看不出上下动作？

这是一个典型的“功能没坏，但 UI 反馈不对”的问题。

### 1. 原始思路

示波器固定绘制某一路，例如 X 轴：

```text
current_ax → waveform
```

如果手势主要发生在 X 轴，这种设计完全没问题。

但当用户做：

- 上下移动
- 前后移动

真正变化最大的可能是 Z 或 Y。

此时 X 轴看到的只是很小的耦合振动。

### 2. 主导轴追踪

项目后来改成动态比较三轴运动幅度。

特别是 Z 轴需要先扣除静态重力基准：

```text
dynamic_Z = |Az - 1.0g|
```

然后比较：

```text
|Ax|
|Ay|
|Az - 1g|
```

选取变化最大的轴作为当前示波器显示轴。

这样：

```text
左右挥动 → X/Y 主导
前后移动 → 对应主导轴
上下抬起 → Z 主导
```

示波器从“固定观察一个变量”升级成“自动寻找最有信息量的变量”。

## 七、OLED 字库太大：一个小 UI 也会影响调试效率

原来的 OLED 字体是 8×16。

字符串：

```text
Y:+0.6
```

大约占用：

```text
6 × 8 = 48 pixels
```

而示波器显示区域只有约 63 pixels 宽。

结果就是：标签几乎覆盖整个波形区域。

### 解决方案

项目在 `oled.c` 中加入独立的 6×8 ASCII 字库，并提供：

```c
OLED_ShowString_6x8(...)
```

把显示宽度从约 48px 压缩到 36px，高度也降低一半。

这看起来只是 UI 小问题，但对于嵌入式调试非常重要：

> 调试界面应该展示数据，而不是遮住数据。

## 八、推理速度：72ms → 32ms

经过上述排障和优化后，项目记录的端侧推理耗时从最初约：

```text
72 ms
```

降低到平均约：

```text
32 ms
```

项目 README 的开发时间线也记录了这一优化结果。fileciteturn53file0

这里需要特别注意：

**32ms 并不等于整个系统 32ms 完成一次动作。**

完整链路还包括：

```text
采集 100 samples
      ↓
DSP / 特征提取
      ↓
模型推理 ≈ 32ms
      ↓
OLED / UART 输出
```

因此在评价 TinyML 系统性能时，应该区分：

- 采样周期
- DSP 时间
- 模型推理时间
- 显示时间
- 完整端到端延迟

这也是下一阶段继续优化时需要重点记录的数据。

## 九、这次排障真正解决了什么？

把整个过程压缩成一张表：

| 问题 | 表现 | 根因 | 解决 |
|---|---|---|---|
| TFLite 依赖膨胀 | 链接大量错误 | 动态解释器依赖过重 | EON + Safe Stub |
| HardFault | MCU 卡死 | 空指针/非法访问 | 静态合法 Stub |
| DSP `-1002` | 特征处理失败 | Heap 太小 | Stack 2KB + Heap 10KB |
| confidence ≈ 0.23 | 动作识别异常 | g / m/s² 量纲失配 | 统一单位 |
| HW RFFT failed | FFT 硬件路径失败 | 16 点不满足 CMSIS 约束 | 软件 FFT fallback |
| 单轴盲区 | 部分动作波形不明显 | 固定 X 轴 | 主导轴动态选择 |
| OLED 遮挡 | 波形看不清 | 8×16 字体过大 | 6×8 紧凑字库 |
| 推理较慢 | ≈72ms | 初始实现开销较高 | 工程优化后 ≈32ms |

## 十、从这个项目得到的工程方法

这次项目最重要的收获其实不是“训练出了一个手势分类器”。

而是形成了一套完整的嵌入式 AI 排障方法：

### ① 先判断问题属于哪一层

```text
传感器
↓
数据
↓
DSP
↓
模型
↓
运行时
↓
MCU 内存
↓
UI
```

不要看到识别错误就直接重新训练模型。

### ② 模型问题首先检查输入契约

确认：

```text
shape
axis order
sampling rate
window length
unit
normalization
```

### ③ MCU 崩溃优先检查内存和依赖

尤其是：

```text
HardFault
OOM
undefined symbol
stack overflow
heap exhaustion
```

### ④ 性能优化不要只看一个数字

应该分别记录：

```text
采样
DSP
Inference
Display
End-to-End
```

### ⑤ UI 也是嵌入式系统的一部分

一个好的调试界面应该帮助定位问题，而不是制造新的问题。

