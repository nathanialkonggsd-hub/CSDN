# TinyML 工程优化实战：从 HardFault 到 32ms 推理

> **STM32 + TinyML 端侧手势识别系列 · 第 77 篇**
>
> 🎯 **本文重点**：复盘模型上 MCU 后真正遇到的工程问题——HardFault、DSP 内存不足、传感器量纲、RFFT 约束、示波器盲区、OLED 显示以及推理性能。

---

## 一、为什么“模型能跑”还不等于项目完成？

前面的链路已经打通：

```text
MPU6050
   ↓
STM32 采集
   ↓
Python / CSV
   ↓
Edge Impulse
   ↓
模型部署
   ↓
STM32 推理
```

但真正的工程问题往往在这一步之后出现。

> ⚠️ **嵌入式 AI 的最后 20%，往往比“让模型第一次跑起来”更难。**

## 二、问题 1：传感器量纲失配

MPU6050 驱动输出的加速度单位、训练数据所使用的单位以及模型输入必须保持一致。

如果训练阶段使用 `g`，而部署阶段却错误地使用 `m/s²`，那么模型看到的数据分布就会发生整体缩放。

```text
训练数据分布
      ≠
MCU 实际输入分布
      ↓
置信度下降 / 误分类
```

### 解决思路

不要先改模型，而是逐层确认：

1. 传感器原始值；
2. 驱动换算；
3. Python 保存值；
4. Edge Impulse 输入值；
5. STM32 最终送入模型的值。

> 💡 **数据单位也是模型接口的一部分。**

---

## 三、问题 2：CMSIS-DSP / RFFT 的约束

TinyML 特征提取并不是“随便调用 FFT”。

某些 CMSIS-DSP RFFT 实现对输入长度、数据布局以及计算方式存在具体约束。

如果训练侧和 MCU 侧的 DSP 参数不一致，就可能出现：

```text
训练正常
   ↓
MCU DSP 参数不匹配
   ↓
特征不同
   ↓
分类结果异常
```

所以部署时必须把：

> **窗口长度、采样率、Feature 参数、DSP 实现**

看成一个整体。

---

## 四、问题 3：DSP Heap `-1002`

在模型真正运行时，曾遇到 DSP heap `-1002`。

本质不是“模型算法错了”，而是 MCU 运行时内存空间不足。

可以简单理解为：

```text
SRAM
├── 全局变量
├── raw_features[300]
├── OLED 缓冲
├── Heap
└── Stack
```

任何一块过大，都可能让整个系统变得不稳定。

### 排查方式

```text
错误码
  ↓
Map 文件
  ↓
Heap / Stack
  ↓
全局数组
  ↓
模型 / DSP 缓冲
```

## 五、问题 4：HardFault

模型部署后还遇到过 HardFault。

这种问题最危险的地方是：

> **它经常发生在“看起来完全合理”的代码之后。**

可能原因包括：

- 栈空间不足
- Heap 不足
- 动态解释器依赖不完整
- 指针 / 缓冲区错误
- DSP 内部内存申请失败

因此处理 HardFault 时，不要只看最后一行业务代码。

应该先建立一个最小化问题链：

```text
HardFault
   ↓
确认发生位置
   ↓
检查栈 / 堆
   ↓
检查模型依赖
   ↓
检查输入长度
   ↓
检查指针与数组边界
```

---

## 六、问题 5：示波器只看一个轴，容易误判

调试三轴加速度时，如果只观察 X 轴，可能出现一个很典型的盲区：

> X 轴看起来“没变化”，不代表整个动作没有变化。

某些动作主要发生在 Y / Z 轴。

因此调试 TinyML 时，最好同时观察三轴数据，或者至少先确认主导变化到底出现在哪个轴。

---

## 七、问题 6：OLED 不是“能显示就行”

最初的 OLED 输出比较偏工程日志：信息多，但空间有限。

后来逐渐压缩到：

```text
状态
手势
Conf
Time
```

并针对 6×8 字体、行空间和结果布局进行优化。

这其实也是嵌入式工程的一部分：

> **UI 不是最后再加的装饰，而是调试信息的另一种输出接口。**

遇到低置信度时，不要直接重新训练模型。

```text

   ↓

内存 / Runtime
   ↓

```

## 九、最明显的一次性能优化：72 ms → 32 ms

在确认模型能够稳定运行后，继续测量端侧推理时间。

优化前：

```text
≈ 72 ms
```

优化后：

```text
≈ 32 ms
```

这里最重要的不是“32 ms”这个数字本身，而是形成了一个工程习惯：

> **不要凭感觉说“快了”，要实际测量。**

项目通过 `HAL_GetTick()` 记录模型调用前后的时间差：

```c
uint32_t t_start = HAL_GetTick();
Model_Run_Inference(...);
last_infer_time = HAL_GetTick() - t_start;
```

## 十、这一轮优化的完整思路

| 问题 | 根因方向 | 工程动作 |
|:---|:---|:---|
| 低置信度 | 输入分布 / 单位 | 对齐数据量纲 |
| DSP 异常 | 参数 / RFFT 约束 | 对齐 Feature 配置 |
| `-1002` | SRAM / Heap | 调整内存布局 |
| HardFault | Runtime / 内存 | 精简依赖、检查栈堆 |
| 单轴盲区 | 观测不完整 | 同时检查三轴 |
| OLED 信息拥挤 | UI 空间有限 | 精简显示 |
| 推理偏慢 | 运行时开销 | 实测并优化 |
